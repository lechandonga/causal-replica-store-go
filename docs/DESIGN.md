# 多副本因果 KV 存储：设计与语义

纯本地实现，零外部依赖。单机内用多个 `Replica` 实例表示副本，用进程内
消息通道 `Network` 模拟不可靠链路（丢包、重复、乱序、断连/重连）。

## 1. 因果版本模型

- 每个副本有一个稳定 ID。每个副本维护**版本向量** `seen[origin] = seq`，
  表示“已知由 origin 发起的前 seq 条操作”。
- 每次本地变更（`Put` / `Delete` / 成员变更）都：
  1. 把本副本序号 `localSeq++`；
  2. 令操作携带当时完整版本向量的快照 `Version`。
- 因果关系由向量比较给出：
  - `A` 支配 `B`（每个分量 `>=` 且至少一个 `>`）⇒ `B` 先于 `A`；
  - 互不可支配 ⇒ **并发（冲突）**。
- **读己之写**：本地写入立刻进入本副本日志并推进本地向量，随后的读必然可见。
- **统一日志**：数据操作（PUT/DELETE）与成员变更事件（加入/退役）共享
  同一套 `(origin, seq)` 稠密序号空间，同步协议只需维护一个游标。

## 2. 冲突与合并规则

对某个键，收集所有操作并按向量时钟做支配淘汰：

1. 被更新墓碑（DELETE）支配的旧墓碑不再可见；
2. **被墓碑支配的旧 PUT 被删除淘汰**——因此乱序迟到的旧值永远不会
   “复活”一个已经因果发生的删除；
3. 存活 PUT 之间去掉被支配者，剩下的才是并发版本。

读取 API 三态：

- 唯一存活值：`Get` 返回该值；
- 无存活值：`Get` 返回 `ErrNotFound`；
- 存在多个并发 PUT，或存活 PUT 与存活墓碑并发：`Get` 返回 `ErrConflict`，
  必须用 `View` 读取全部冲突版本。

冲突**绝不静默覆盖或丢弃**。解决是一次显式的新本地操作：

- `Resolve(key, value)`：把所有存活冲突版本的向量并入本地向量后再写入，
  新版本严格支配被解决的全部版本；
- `ResolveDelete(key)`：同样并入冲突向量，但写入墓碑，表示“删除胜出”。

解决操作随后像普通更新一样传播，所有副本收敛到同一个确定结果。

## 3. 同步语义（增量、幂等、最终一致）

### 3.1 增量交换

同步是无状态的、可任意重复的双向交换：

1. 双方交换摘要 `(Membership, seen, gcFloor)`；
2. 各自用 `EntriesAfter(peerSeen)` 只回传对方缺失的日志事件；
3. 接收方 `ApplyEntries` 幂等落地。

`SyncToConvergence` 反复交换直到双方 `seen` 完全相同且成员纪元一致。

### 3.2 故障下的正确性

- **重复**：按 `(origin, seq)` 去重，重复事件绝不二次应用。
- **乱序**：同一 origin 的 seq 必须稠密。乱序先到（如收到 1、3）只落地
  稠密前缀 1，并返回 `GapError`；下一轮对端按水位重传 2 后收敛。
- **丢失**：消息丢失等价于这一轮什么都没发生，后续轮次基于最新 `seen`
  重传缺失部分（at-least-once + 接收端幂等 = effectively-once）。
- **中途断开**：`ExchangeOnce`/单跳本身是幂等的，断连时部分应用的稠密
  前缀无需回滚；`Network.Reconnect` 后再次驱动同步即可收敛。断连期间双方
  的本地写入全部保留，重连后作为并发版本同时可见。

### 3.3 网络模拟

`Network` 用带缓冲 channel 作为收件箱，按有向链路 `FaultProfile` 注入：

- `DropRate` 丢包、`DupRate` 重复、`ReorderRate` 延迟一轮制造乱序、
  `BreakEvery`/`Disconnect` 断连；
- 所有随机性来自显式种子，**同种子多次运行结果完全一致**（见
  `TestDeterminismAcrossRuns`）；
- `Stats` 暴露实际丢/重/乱序/断连计数，便于验证故障确实发生且被消化。

## 4. 删除与安全回收（GC）

删除是普通的墓碑操作，参与因果比较与同步。

### 4.1 安全水位

每个副本记录每个**当前活跃成员**最近自报的 `seen`。GC 的逐 origin 安全
水位 = 全体活跃成员自报水位的**逐分量最小值**：

- 从未自报过的成员视为对所有 origin 贡献 0 ⇒ 该 origin 一条都不能回收；
- 这保证“还有成员没见过的操作”绝不被物理删除。

### 4.2 墓碑回收条件

墓碑只有在**支配该键全部兄弟操作**（删除已因果确定胜出）时才允许回收。
若仍有并发 PUT（删除与更新竞争尚未解决），墓碑保留，直到显式
`Resolve`/`ResolveDelete` 后才可能回收。

### 4.3 回收水位与防复活

回收把 `gcFloor[origin]` 单调抬升到安全水位。此后任何
`seq <= gcFloor` 的迟到/重传消息（含旧 PUT、旧墓碑）都被幂等忽略，
因此 GC 之后旧数据不可能因乱序消息复活（见
`TestBusinessStaleOpsAfterGCIgnored`）。

## 5. 回收之后长期离线副本回归

这是分布式删除回收中最危险的场景，处理方式是**确定且可解释**的：

- 同步握手时，若对端自报 `seen` 中某 origin 低于本副本 `gcFloor`，
  说明中间操作已被物理回收，增量同步无法补齐（`PeerNeedsSnapshot`）。
- 此时**不允许**该副本继续增量推送它本地的陈旧日志（否则可能复活已删
  数据），而是由最新副本下发**全量快照**（当前成员视图、seen、gcFloor、
  存活操作集合），陈旧副本用快照整体重置。
- 结果确定：回归副本与集群状态完全一致，已删除数据不复活，存活数据不丢失。

### 成员退役 / 损毁

为避免“某成员永久消失导致全员 GC 永远无法推进”，成员变更（加入/退役）
是统一日志上的因果事件，带单调 `Epoch`：

- `RetireMember` 要求退役前已收到过该成员的水位自报，避免退役一个可能
  仍持有未知写入的成员；
- 退役后该成员不再计入 GC 全员集合；
- 被退役成员日后回归时，通过同步识别到自己已不在成员视图，`IsRetired()`
  为真，旧身份的本地写被拒绝；它只能通过 `AddMember` 以**新身份**加入并
  用快照灌装。旧身份的数据不会复活。

## 6. 代码结构

| 文件 | 职责 |
| --- | --- |
| `clock.go` | 版本向量及因果比较 |
| `operation.go` | PUT/DELETE 操作、成员变更事件、统一日志条目 |
| `store.go` | 副本状态、本地 Put/Delete/Resolve、快照 |
| `view.go` | 键视图、冲突判定、幂等应用 |
| `log.go` | 统一日志、增量选取 `EntriesAfter`、`ApplyEntries` |
| `membership.go` | 成员加入/退役与纪元推进 |
| `gc.go` | 安全水位、墓碑回收、`gcFloor`、快照需求判定 |
| `network.go` | 通道模拟网络与确定性故障注入 |
| `sync.go` | 双向增量同步、收敛循环、网络驱动、快照重同步 |

## 7. 验证方法

```bash
# 全部单测（-v 可看到每个业务与用例的中文日志）
go test -v ./...

# 竞态检测 + 多次重复运行
CGO_ENABLED=1 go test -race -count=5 ./...

# 端到端演示（冲突 / 乱序 / 断连重连 / GC / 离线回归）
go run ./cmd/demo
```

测试按业务组织，每个业务用例都打印“做了什么、预期什么”：

1. 本地因果（读己之写）；
2. 并发冲突可见且可显式解决；
3. 删除与并发写竞争；
4. 乱序与重复同步的幂等性；
5. 不可靠网络下的断连重连与最终收敛；
6. 删除的安全回收（旧值不复活、未全员见不回收、并发墓碑暂缓回收）；
7. 回收后离线副本回归的快照重同步、退役成员以新身份加入；
8. 同一故障种子连续多轮结果一致（确定性）。
